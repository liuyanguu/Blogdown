# Quarto Research Blog Migration Design

## Goal

Migrate the personal research blog from the current Hugo/blogdown XMag site to a cleaner Quarto blog while keeping R as the authoring and computation language. All existing posts should be migrated, the design should feel modern and research-oriented, and the generated site should continue publishing to `C:/liuyanguu/liuyanguu.github.io`.

## Approved Direction

Use a full Quarto migration with new clean canonical URLs. The new site should use paths like `/posts/2025-supernationals-viii/` rather than preserving every old Hugo path shape. Existing Hugo post URLs that can be derived from migrated front matter should redirect to the new locations.

The visual direction is "Research Lab": clean, professional, readable, and modern. It should feel like a polished personal research notebook for statistics, population data, R workflows, maps, chess analyses, and reproducible visual essays.

## Current Context

The current source repo is `C:/liuyanguu/Blogdown`. The active Hugo/blogdown source lives in `hugo-xmag/`, with generated output in `hugo-xmag/public/`. The deployed GitHub Pages repo is separate at `C:/liuyanguu/liuyanguu.github.io`.

The current environment has Quarto `1.9.36` installed. Hugo is not on `PATH`, and the current R library does not have `blogdown` installed. This makes a Quarto migration preferable to investing in the old Hugo/blogdown toolchain.

## Architecture

The root of `C:/liuyanguu/Blogdown` becomes the Quarto source site. The new source layout should be:

```text
Blogdown/
  _quarto.yml
  index.qmd
  about.qmd
  posts/
    2025-supernationals-viii/
      index.qmd
    2024-national-k12-rating-standing/
      index.qmd
    2024-children-under-5-worldwide/
      index.qmd
  scripts/
    setup.R
    build.R
    migrate-posts.R
  resources/
    data/
    figures/
  docs/
    superpowers/
```

The old `hugo-xmag/` tree should remain untouched at first as a migration source and rollback reference. Once the Quarto site is verified, old generated artifacts can be cleaned up in a separate, explicit cleanup pass.

Quarto output should publish to `C:/liuyanguu/liuyanguu.github.io`. The implementation should prefer a documented build script over relying on memory or RStudio state.

## Content Migration

All existing source posts under `hugo-xmag/content/` should be migrated. Plain `.Rmd` posts and leaf-bundle posts such as `content/post/<slug>/index.Rmd` should become Quarto post folders under `posts/<clean-slug>/index.qmd`.

Rendered `.html` files under `content/post/` should not be treated as canonical source when an `.Rmd` exists. They can be used only as visual/reference material during migration checks.

Front matter should be normalized to Quarto-friendly YAML:

```yaml
---
title: "Post title"
author: "Yang Liu"
date: "YYYY-MM-DD"
categories:
  - Category
tags:
  - Tag
execute:
  freeze: auto
---
```

Existing categories and tags should be preserved where useful, but obviously stale categories such as sample theme/demo categories should be removed from migrated real content.

## URL And Redirect Strategy

New canonical post URLs should use `/posts/<clean-slug>/`.

For each migrated post, generate a redirect from the old Hugo permalink when it can be derived from the date and slug, for example:

```text
/post/2025/05/15/2025-supernationals-viii-a-once-in-four-years-chess-spectacle/
  -> /posts/2025-supernationals-viii/
```

The default redirect mechanism should be lightweight HTML redirect pages generated by the migration/build workflow. If a source post is missing the date or slug needed to derive the old Hugo permalink, the migration script should write that post to a redirect review report for manual handling. The implementation should verify at least three old URLs in the browser.

## Visual Design

Use a restrained "Research Lab" style:

- Light background, crisp white content surfaces, and subtle borders.
- Sans-serif UI and navigation with comfortable article typography.
- A readable code style with horizontal scrolling for long R code.
- Homepage sections for a short intro, recent posts, selected topics, and featured analyses.
- Post listings with date, category/tag metadata, short descriptions, and optional thumbnails from generated figures.
- Mobile-first layout that keeps navigation, post cards, tables, and figures readable.

The design should not use a marketing landing page. The first screen should immediately show the blog identity and recent research content.

## R Execution Strategy

R remains the primary computation language. Quarto should render R chunks through knitr.

Recent and actively maintained posts should be executable when dependencies are available. Older posts with obsolete packages or fragile historical data dependencies should be migrated with frozen output after initial validation, so the site can build reliably without rerunning every old analysis each time.

The migration should separate:

- Site build dependencies: Quarto, knitr, rmarkdown, yaml, htmltools, and other core packages.
- Post-specific analysis dependencies: ggplot2, data.table, sf/terra, plotly, shiny-related examples, and package-specific dependencies used by older posts.

Deprecated packages such as `rgdal`, `leafletCN`, and `ggsn` should not be part of the default setup script. Where old posts mention them as historical examples, the prose should make clear that the post is archival or that modern replacements are preferred.

## Scripts

Replace `note.R` with clearer scripts:

- `scripts/setup.R`: checks for required packages, installs missing CRAN packages only after showing the list, and prints Quarto/R versions.
- `scripts/build.R`: renders the Quarto site and reports the output directory.
- `scripts/migrate-posts.R`: performs repeatable mechanical migration from Hugo/blogdown post sources into Quarto post folders.

The scripts should avoid running a dev server or installing a long package list as a side effect of sourcing a notes file. Commands should be explicit and documented in `README.md`.

## Proofreading And Code Cleanup

Proofreading should focus first on:

- `README.md`
- `about.qmd`
- The homepage intro
- Recent posts from 2024 and 2025
- Setup and build scripts

All migrated posts should get a mechanical cleanup pass for common issues: "Github" to "GitHub", "Blogdown" to "blogdown" when referring to the R package, obvious typos, broken Markdown lists, malformed headings, and inconsistent capitalization.

Code cleanup should preserve analytical results. Refactors should be limited to readability, explicit package namespaces where helpful, stable paths, and replacing setup patterns that no longer run.

## Data And Assets

Large data files should not be duplicated unnecessarily. Existing data under `Data/` can remain where it is during migration, but new Quarto posts should refer to stable paths through a small helper or documented convention.

Post-generated figures should stay with each post when they are needed for frozen output. Shared static images such as the author photo can move into a Quarto-friendly assets folder if that simplifies paths.

## Error Handling

The migration should classify issues instead of silently failing:

- Build blockers: Quarto render errors, missing files required by the current site, broken YAML.
- Post execution blockers: missing obsolete packages, unavailable external data, code that depends on old APIs.
- Content warnings: broken links, missing alt text, malformed summaries, stale wording.

Build blockers should be fixed before completion. Post execution blockers can be handled by freezing a verified migrated output or marking the post as archival, as long as the post remains readable and its old result is preserved.

## Testing And Verification

Verification should include:

- `quarto check`
- A full `quarto render`
- A local preview or static browser check of the homepage, about page, listing page, and representative migrated posts.
- Browser checks for desktop and mobile widths.
- Redirect checks for at least three old Hugo URLs.
- A search for broken local links and missing referenced images.
- Git status checks in both `C:/liuyanguu/Blogdown` and `C:/liuyanguu/liuyanguu.github.io`.

The final implementation should not claim success until the rendered site has been opened and visually checked.

## Documentation

`README.md` should explain:

- The site is now built with Quarto.
- Posts are written in Quarto/R Markdown with R code chunks.
- How to install/check dependencies.
- How to preview locally.
- How to render to `C:/liuyanguu/liuyanguu.github.io`.
- How to publish the generated GitHub Pages repo.
